# t_wada 式 TDD で実装する

t_wada（和田卓人）の TDD 手法に従い、**Red → Green → Refactor** のリズムを厳守して実装を進めてください。

## 基本サイクル

```
Red   → 失敗するテストを 1 つだけ書く
Green → テストを通す最小限のコードを書く（仮実装でも可）
Refactor → テストが通ったままコードを整理する
```

## 作業手順

### 0. テストリスト（TODO リスト）を作る

実装を始める前に、書くべきテストを箇条書きで列挙する。
実装中に気づいた新しいケースもすぐリストに追加する。
一度に複数のテストを書かない——リストに残しておいて次に回す。

### 1. Red フェーズ

- テストリストから **1 つだけ** 選んでテストを書く
- テストは意図を明確に表す名前にする（例: `石がないセルはstoneClassを持たない`）
- テストを実行して **赤（失敗）** を確認してから次へ進む
- コンパイルエラーも Red の一種として扱う

### 2. Green フェーズ

テストを通す最短経路を取る。選択肢は 3 つ：

| 戦略 | 使いどき |
|------|--------|
| **仮実装 (Fake It)** | 何をすべきか不明なとき。まず `return "固定値"` で通す |
| **三角測量 (Triangulation)** | 仮実装で通した後、別のテストケースを追加して一般化を強制する |
| **明白な実装 (Obvious Implementation)** | 実装内容が明らかなとき。一気に書く |

- テストが通ったら **即座に確認**（`npm run test:unit` など）
- 通ったら Green を宣言し、Refactor へ

### 3. Refactor フェーズ

- テストが **全て通っている状態** でのみリファクタリングする
- 重複を除去する（DRY）
- 意図を明確にする（変数名・関数名の改善）
- Refactor 中は新機能を追加しない
- Refactor 後も必ずテストを実行して Green を確認する

---

## 実践ルール

- **小さく刻む**: 1 サイクルは 5〜15 分以内に収める
- **テストから書く**: プロダクションコードより先にテストを書く（例外なし）
- **失敗を確認する**: Red を確認せずに Green へ進まない
- **一度に 1 つ**: Red フェーズで複数のテストを書かない
- **リズムを守る**: 詰まったら仮実装に戻る

## 何をどこに書くか（t_wada の原則）

| 場所 | 書くこと | 書かないこと |
|------|--------|------------|
| **コード** | How（どう実現するか） | Why / What |
| **テストコード** | What（何をテストするか・仕様） | How |
| **コミットログ** | Why（なぜこの変更が必要か） | How / What |
| **コードコメント** | Why not（なぜその選択をしたか・他の選択肢を排除した理由） | How / What |

### 具体例

```typescript
// コード: How だけ（名前で What は伝わる）
function reverseStones(board: Board, from: Point, direction: Direction): void {
  // ...
}

// テスト: What（仕様・振る舞い）を宣言的に書く
it("石を置いた後、挟んだ相手の石が反転する", () => { ... });
it("置ける場所がない場合はパスになる", () => { ... });

// コードコメント: Why not（なぜ他の実装を選ばなかったか）
// Immutable にしないのは、Proxy による Vue 3 のリアクティビティを使うため。
// 純粋関数 + 新 Board 返却にすると reactive() が機能しない。
```

## このセッションでの進め方

1. まず **テストリスト** をチャットに出力する
2. リストの先頭から 1 件選んで Red → Green → Refactor を回す
3. 1 サイクル完了したら次のテストをリストから選ぶ
4. 全テスト完了後にコミットする

テストリストの出力から始めてください。
