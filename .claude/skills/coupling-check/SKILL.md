# 結合度合いのチェック（均衡結合モデル）

Vlad Khononov『ソフトウェア設計の結合バランス』の **均衡結合モデル** で、
モジュール間の結合を診断する。

## 大原則

> **ゴールは結合の強度を「最小化」することではない。**
> **実装・進化・保守が容易なモジュラーシステムを設計することだ。**

結合は悪ではない。良し悪しは **3つの次元のバランス** で決まる。
「常に疎結合にせよ」は誤り。強く結びつくものは近くに置けばよい。

| 次元 | 問い |
|------|------|
| **強度 (Strength)** | 2つのモジュールはどれだけ知識を共有しているか |
| **距離 (Distance)** | コードベース上・組織上どれだけ離れているか |
| **変動性 (Volatility)** | どれだけ頻繁に変更されるか |

スコアリングに使う 1〜10 のスケール表と均衡結合方程式の解説は
`references/coupling-scales.md` にある。**Step 2 に入る前に読むこと。**

---

## 🚨 検出すべき2大危険パターン

どちらも **複雑性 × 高変動性** の組み合わせ。これを最優先で潰す。

### ① 高強度 × 遠距離 × 高変動性 → 大域的複雑性
別サービス・別モジュールに、よく変わるビジネスロジックが**重複/強依存**している。
> 例：`reversi.ts` の合法手判定ロジックを、別サービスの CPU 側でコピー実装

### ② 低強度 × 近距離 × 高変動性 → 局所的複雑性
無関係な機能が1つの巨大クラス/ファイルに同居し、それがよく変わる。
> 例：`game.ts` ストアに、ゲーム進行・スコア集計・履歴・通知が全部入り

---

## 診断フロー

### Step 0. 対象範囲を決める

| 引数 | 範囲 | 用途 |
|------|------|------|
| なし / `diff` | 現在ブランチの変更差分 | レビュー時。新たに生まれた/悪化した結合を見る |
| `<モジュール名>` | 指定モジュールの依存 | 設計相談・リファクタ判断 |
| `all` | コードベース全体 | 棚卸し・健全性監査 |

```bash
# diff 範囲の把握
git diff main...HEAD --stat
# 変動性の補助シグナル（コミット頻度）
git log --oneline --since="6 months ago" -- <path> | wc -l
```

### Step 1. 結合点を洗い出す（2種類を必ず両方見る）

**(a) 依存による結合（import で繋がっている）**
「誰が誰に依存しているか」を列挙する。知識は依存と逆向きに流れる
（A が B を import → B が上流／A が下流）。

**(b) 同居による結合（import の線が無い）** ← 見落とし注意
1つのファイル/クラス/ストアに**無関係な責務が同居**していないかを列挙する。
危険パターン②（局所的複雑性）は依存線が無いことが多く、(a) だけ見ると検出できない。
「このファイルは何種類の理由で変更されるか」を数え、複数の責務が混在していれば結合点候補とする。

このプロジェクトの主な結合点の例：
- (a) `VCell.vue` → `stores/game.ts`（アクション呼び出し）
- (a) `VGame → VBoard → VRow → VCell`（Props の階層）
- (a) `stores/game.ts` → `models/reversi.ts`（ドメインロジック利用）
- (a) `models/cpu.ts` → `models/reversi.ts`（盤面評価）
- (b) `stores/game.ts` 内にゲーム進行・CPU制御・undo履歴・モード設定が同居（責務ペア）

### Step 2. 各結合点を3次元でスコアリング

`references/coupling-scales.md` のスケール表を使い、**強度・距離・変動性**を 1〜10 で付ける。

- 強度：境界越しに「何を」共有しているかで判定（実装詳細か / モデルか / コントラクトか）
- 距離：最も近い共通の祖先ディレクトリ＋所有チーム
- 変動性：知識を公開する上流モジュールのサブドメイン種別（＋ git log）

> ⚠️ **強度・変動性は「ファイル全体」ではなく「境界を越えて共有している知識」に対して測る。**
> 例：内部実装が頻繁に変わるストアでも、共有しているのが安定した公開API（コントラクト）なら、
> その結合の実効変動性は低い。git のコミット数は churn の偽陽性に注意（本書のソースコード分析の警告）。

> ⚠️ **機能結合・対称機能結合では上流/下流の区別が無く、知識は双方向に流れる**（本書：両方とも上流とみなす）。
> 共有しているルールは**どちらが変わっても**変わるため、変動性は**両側のうち大きいほう（max）**を採る。
> 片側だけ見ると「変わりやすい側＋安定した側」を安全と誤判定し、大域的複雑性を見落とす。

### Step 3. 均衡度を計算する

```
均衡度 = max( |強度 - 距離| , 10 - 変動性 ) + 1
```

**均衡度が高い(10に近い) ＝ 良い**（モジュラー）／ **低い(1に近い) ＝ 悪い**（複雑）。
式が何を意味しているか（強度と距離は XOR であるべき等）は `references/coupling-scales.md` を参照。

### Step 4. 危険パターンを判定する

- 均衡度が **低い（目安 4 以下）** ＝ 要対処
- 上の2大危険パターンに該当しないか確認
- 均衡度が高くても、変動性に支えられているだけ（強度・距離は悪い）なら、
  **変動性が上がった瞬間に破綻する** 予備軍として記録する

### Step 5. 再均衡化を提案する

どの危険パターンかで打ち手の**向き**が逆になる。まず①か②かを見極める。

**危険パターン①（大域的複雑性：高強度 × 遠距離 × 高変動性）→ 値を下げる**

| 下げる次元 | リファクタリング手段 |
|-----------|-------------------|
| **強度↓** | 侵入結合→コントラクト結合へ。API/DTO で境界を明示し内部モデルを隠す。共有DB直読みをやめる |
| **距離↓** | 重複ロジックを1箇所に**抽出して集約**。強く結びつくものは同じモジュール/同じチーム所有に寄せる |
| **変動性↓** | 原則ビジネス起因で制御不可。サブドメイン種別の変化（支援→コア等）を監視し、変わったら強度か距離を調整する |

> 強度を下げられない場合（業務がトランザクション機能結合を要求する等）は、
> 無理に下げず **距離を縮める**。それが最も実践的な打ち手になることが多い。

**危険パターン②（局所的複雑性：低強度 × 近距離 × 高変動性）→ 分離して距離を「広げる」**

①と違い、強度も距離も既に低く、変動性は制御不可。値を下げる手は使えない。
正しい打ち手は逆向き＝**同居している無関係な責務を別モジュールに分離し、距離・カプセル化を増やす**。

| 手段 | 具体例 |
|------|--------|
| **責務の分離** | 巨大ストア/クラスから無関係な責務を別ファイル（composable・別モジュール）へ抽出する |
| **境界の付与** | 抽出した責務に明確なインターフェイスを与え、本体は公開APIだけで呼ぶ（強度を契約結合側へ） |

診断結果は次の表でまとめる。

|--------|------|------|--------|--------|------|--------------|
| cpu.ts → reversi.ts | 8 (機能) | 2 | 10 | **7** | ✅ 良好（高凝集） | 維持。強い結合が近接しているので健全 |

## このセッションでの進め方

1. Step 0 で対象範囲を確認する（無指定なら diff）
2. `references/coupling-scales.md` を読む
3. Step 1〜2 で結合点を洗い出してスコアリングし、上の表を埋める
4. Step 3〜4 で均衡度を計算し危険パターンを判定する
5. Step 5 で再均衡化を提案する（実際の修正は `/tdd` で進める）

結合点の洗い出しと出力表の提示から始めてください。
