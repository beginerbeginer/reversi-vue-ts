# 結合度合いのチェック（均衡結合モデル）

Vlad Khononov『ソフトウェア設計の結合バランス』の **均衡結合モデル** で、
モジュール間の結合を診断する。

## 大原則

> **ゴールは結合の強度を「最小化」することではない。**
> **実装・進化・保守が容易なモジュラーシステムを設計することだ。**

結合は悪ではない。良し悪しは **3つの次元のバランス** で決まる。
「常に疎結合にせよ」は誤り。強く結びつくものは近くに置けばよい。

---

## 結合の3次元（スコアは 1〜10）

| 次元 | 問い | 高いと |
|------|------|--------|
| **強度 (Strength)** | 2つのモジュールはどれだけ知識を共有しているか | 一方の変更が他方に波及しやすい |
| **距離 (Distance)** | コードベース上・組織上どれだけ離れているか | 一緒に変更する労力が大きい |
| **変動性 (Volatility)** | どれだけ頻繁に変更されるか | 設計の欠陥が顕在化しやすい |

### 強度スケール（統合強度モデル）

弱い＝良い。**「何を共有しているか」** で判定する。

| 値 | レベル | 何を共有しているか | コードでの見分け方 |
|----|--------|------------------|------------------|
| **1** | コントラクト結合 | 統合専用モデル（API/DTO/コマンド）のみ | 公開APIや専用の型越しにやり取り。内部モデルは隠蔽 |
| **3** | モデル結合 | ドメインモデルそのもの | ドメインの型を境界越しにそのまま渡す/共有DBを読む |
| **8** | 機能結合 | ビジネスロジック・ルール・不変条件 | 同じ業務ルール/順序/トランザクションに依存 |
| **9** | 対称機能結合 | 同じ機能を**重複実装**（DRY違反） | 同一ロジックが2箇所にコピーされ、同時変更が必要 |
| **10** | 侵入結合 | 実装詳細（private・内部構造） | private参照・リフレクション悪用・他者の運用DB直叩き |

機能結合(8)の細かい度合い（弱→強）：
シーケンシャル機能結合（順序依存）→ 値/同一性のコナーセンス → トランザクション機能結合 → 対称機能結合(9)。

### 距離スケール

近い＝良い。**2つのモジュールの「最も近い共通の祖先」** で測る。

| 値 | カプセル化境界 |
|----|--------------|
| **1** | 同じオブジェクト/クラスのメソッド間 |
| **2** | 同じ名前空間・モジュール内の別オブジェクト |
| **3〜7** | 別の名前空間・ディレクトリのオブジェクト |
| **8** | 別ライブラリ/パッケージ |
| **9** | 分散システムの別サービス |
| **10** | 別ベンダーが実装した別システム |

ソシオテクニカル補正：**所有チームが離れるほど実質距離は増える**（コンウェイの法則）。
非同期通信はライフサイクル結合を下げ、距離を増やす方向に働く。

### 変動性スケール

低い＝安全。**サブドメインの種類** が第一の手がかり。

| 値 | 対象 | 特徴 |
|----|------|------|
| **1** | 進化しないレガシー | もう変更されない |
| **3** | 支援サブドメイン / 汎用サブドメイン | 単純 or 解決済み。変更頻度は低い |
| **10** | コアサブドメイン | 競争優位の源泉。最も頻繁に変わる |

| サブドメイン | 競合優位 | 変動性 | 例（このプロジェクト） |
|------------|---------|--------|------|
| コア | 高い | **高い** | ゲームのコアルール（着手・反転・合法手判定） |
| 支援 | 低い | 低い | スコア表示・パス通知などの周辺UI |
| 汎用 | 低い | 低い | ルーティング・テーマ等の出来合い機能 |

補助シグナル：`git log` のコミット頻度。変更が多いファイルは変動性が高い傾向。
ただし **偽陽性/偽陰性に注意**（リファクタの多発 / まだ書かれていないコア）。

---

## 均衡結合方程式

```
モジュール性 = |強度 - 距離| + 1
均衡度       = max( |強度 - 距離| ,  10 - 変動性 ) + 1
```

- **均衡度が高い(10に近い) ＝ 良い**（モジュラー）／ **低い(1に近い) ＝ 悪い**（複雑）
- 直感：**強度と距離は対照的であるべき（XOR）**。
  強く結合するなら近くに、遠いなら弱く結合せよ。
- **変動性が低ければ不均衡は許容される**。変わらないものは痛みを生まない。

### 2値で覚える早見表（高=1 / 低=0、距離は遠=1 / 近=0）

| 式 | 意味 |
|----|------|
| 安定性 = NOT (変動性 AND 強度) | 強くても変わらなければ安定 |
| 変更コスト = 変動性 AND 距離 | 遠くてよく変わると高コスト |
| モジュール性 = 強度 XOR 距離 | 強度と距離が対照的なら良い |
| 大域的複雑性 = 強度 AND 距離 | 強い結合が遠くに散っている |
| 局所的複雑性 = NOT 強度 AND NOT 距離 | 無関係なものが近接している |

---

## 🚨 検出すべき2大危険パターン

どちらも **複雑性 × 高変動性** の組み合わせ。これを最優先で潰す。

### ① 高強度 × 遠距離 × 高変動性 → 大域的複雑性
別サービス・別モジュールに、よく変わるビジネスロジックが**重複/強依存**している。
> 例：`reversi.ts` の合法手判定ロジックを、別サービスの CPU 側でコピー実装

### ② 低強度 × 近距離 × 高変動性 → 局所的複雑性
無関係な機能が1つの巨大クラス/ファイルに同居し、それがよく変わる。
> 例：`game.ts` ストアに、ゲーム進行・スコア集計・履歴・通知が全部入り

## 診断フロー

### Step 0. 対象範囲を決める

| 引数 | 範囲 | 用途 |
|------|------|------|
| なし / `diff` | 現在ブランチの変更差分 | レビュー時。新たに生まれた/悪化した結合を見る |
| `<モジュール名>` | 指定モジュールの依存 | 設計相談・リファクタ判断 |
| `all` | コードベース全体 | 棚卸し・健全性監査 |

```bash
# diff 範囲の把握
git diff main...HEAD --stat
# 変動性の補助シグナル（コミット頻度）
git log --oneline --since="6 months ago" -- <path> | wc -l
```

### Step 1. 結合点（依存）を洗い出す

「誰が誰に依存しているか」を列挙する。知識は依存と逆向きに流れる
（A が B を import → B が上流／A が下流）。

このプロジェクトの主な結合点の例：
- `VCell.vue` → `stores/game.ts`（アクション呼び出し）
- `VGame → VBoard → VRow → VCell`（Props の階層）
- `stores/game.ts` → `models/reversi.ts`（ドメインロジック利用）
- `models/cpu.ts` → `models/reversi.ts`（盤面評価）

### Step 2. 各結合点を3次元でスコアリング

上のスケール表を使い、**強度・距離・変動性**を 1〜10 で付ける。
- 強度：境界越しに「何を」共有しているかで判定（実装詳細か / モデルか / コントラクトか）
- 距離：最も近い共通の祖先ディレクトリ＋所有チーム
- 変動性：上流モジュールのサブドメイン種別（＋ git log）

> ⚠️ **強度・変動性は「ファイル全体」ではなく「境界を越えて共有している知識」に対して測る。**
> 例：内部実装が頻繁に変わるストアでも、共有しているのが安定した公開API（コントラクト）なら、
> その結合の実効変動性は低い。git のコミット数は churn の偽陽性に注意（本書のソースコード分析の警告）。

### Step 3. 均衡度を計算する

```
均衡度 = max( |強度 - 距離| , 10 - 変動性 ) + 1
```

### Step 4. 危険パターンを判定する

- 均衡度が **低い（目安 4 以下）** ＝ 要対処
- 上の2大危険パターンに該当しないか確認
- 均衡度が高くても、変動性に支えられているだけ（強度・距離は悪い）なら、
  **変動性が上がった瞬間に破綻する** 予備軍として記録する

### Step 5. 再均衡化を提案する

不均衡な次元の値を下げる。**1つの次元をゼロにすれば他の高い値を相殺できる。**

| 下げる次元 | リファクタリング手段 |
|-----------|-------------------|
| **強度↓** | 侵入結合→コントラクト結合へ。API/DTO で境界を明示し内部モデルを隠す。共有DB直読みをやめる |
| **距離↓** | 重複ロジックを1箇所に**抽出して集約**。強く結びつくものは同じモジュール/同じチーム所有に寄せる |
| **変動性↓** | 原則ビジネス起因で制御不可。サブドメイン種別の変化（支援→コア等）を監視し、変わったら強度か距離を調整する |

> 強度を下げられない場合（業務がトランザクション機能結合を要求する等）は、
> 無理に下げず **距離を縮める**。それが最も実践的な打ち手になることが多い。

## 出力フォーマット

診断結果は次の表でまとめる。

| 結合点 | 強度 | 距離 | 変動性 | 均衡度 | 判定 | 推奨アクション |
|--------|------|------|--------|--------|------|--------------|
| cpu.ts → reversi.ts | 8 (機能) | 2 | 10 | **7** | ✅ 良好（高凝集） | 維持。強い結合が近接しているので健全 |
| （重複ロジック例） | 9 (対称) | 9 | 10 | **1** | 🚨 大域的複雑性 | ロジックを1箇所に抽出して距離を消す |

計算例：`max(|8-2|, 10-10)+1 = max(6,0)+1 = 7` ／ `max(|9-9|, 10-10)+1 = 1`

最後に **最優先で対処すべき結合 Top3** を均衡度の低い順に提示する。

## このセッションでの進め方

1. Step 0 で対象範囲を確認する（無指定なら diff）
2. Step 1〜2 で結合点を洗い出してスコアリングし、上の表を埋める
3. Step 3〜4 で均衡度を計算し危険パターンを判定する
4. Step 5 で再均衡化を提案する（実際の修正は `/tdd` で進める）

結合点の洗い出しと出力表の提示から始めてください。
