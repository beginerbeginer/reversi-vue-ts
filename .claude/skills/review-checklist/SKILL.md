# レビュー指摘チェックリスト

過去の PR レビュー（codex / Copilot）で実際に受けた指摘の一般化。
**PR 作成前にこのリストで自己点検し、該当があれば直してから出す。**

## 運用ルール（蓄積ループ）

1. 新しい指摘を受けたら、対応コミットを作る前に**このファイルの該当セクションへ追記**する
2. 追記してからレビュースレッドに返信・解決する
3. 出典（PR 番号）を必ず残す。後から「なぜこのルールがあるのか」を辿れるようにする

---

## コード

- [ ] **終端・境界条件をヒューリスティックで評価していないか**。ゲーム終了・EOF・空集合などの
      終端は実際の結果で判定する。位置重み評価が「負ける終局」を「勝つ終局」より高く評価し、
      読み切れる勝ちを捨てるバグの実例あり（#372 で codex と Copilot の**両方**から同一指摘）
- [ ] **ループ・描画パスの中に線形探索がないか**。`v-for` 内の `Array.some()` は
      セル数 × リスト長の照合になる。変更時だけ再構築する `computed` + `Set` に置き換える（#355）
- [ ] **「時間制約」を固定パラメータで代用していないか**。「depth 5 なら 3 秒以内」のような
      決め打ちは、計測した局面が最悪ケースとは限らず環境性能にも依存する。実際に
      95,917 ノード・別環境で 6.7 秒に達する局面が見つかった。**時間制約は時間で守る**
      （反復深化 + デッドライン）。ベンチは「平均」ではなく最悪ケースで判断する（#379 codex）

## 禁止ルールを lint で強制するとき

- [ ] **禁止したい API の宣言経路を全部数えたか**。1 経路だけ塞いで「禁止した」と書くと
      抜け道が残る。emit 禁止で `defineEmits` だけを塞いだところ、Options API の
      `emits:` オプション・`defineModel()`・`ctx.emit`・`setup(props, { emit })` が
      すべて通り抜けた。しかも `emits:` を宣言すると `vue/require-explicit-emits` が
      満たされ、テンプレートの `$emit` まで通る（#392 codex）
- [ ] **各経路に違反コードを書いて、実際に error になることを確認したか**。
      設定を書いただけで「効くはず」と報告しない。プローブを作って検証し、削除する
- [ ] **CI の path フィルタが、変更した設定ファイルを拾うか確認したか**。
      `ci.yml` のフィルタが `.eslintrc*` のままで、フラットコンフィグ移行後の
      `eslint.config.mjs` を拾っておらず、lint 設定を変えても CI が起動しなかった（#392）
- [ ] **重い同期処理を UI スレッドで実行していないか**。CPU 思考のような長時間処理は
      その間ブラウザ全体が固まる。デッドラインを設けるか Web Worker に逃がす（#379 codex）
- [ ] **比率(%)と固定値(px)を混在させていないか**。`inset: 3%` はセルが縮むと
      `border: 2px` を下回り描画が破綻する。`max(2px, 3%)` のように下限をクランプする（#341）

## テスト

- [ ] **重い・非決定的なテストを追加していないか**。数百回の自己対戦のような統計テストは
      タイムアウト・flaky の温床。勝率などの計測は開発時スクリプトで行い CI に入れない（#321 codex / #337）
- [ ] **テストを削除・変更した後、describe 名やファイル名が中身と一致しているか**。
      「CPU 強さ評価」という名前でガードテストだけが残る、という不一致を残さない（#321 Copilot）
- [ ] **アルゴリズムの意思決定を検証しているか**。「合法手を返す」だけでは
      ミニマックスが機能しているか検知できない。固定盤面で「貪欲となら異なる、この手を選ぶ」
      まで固定する（#321 Copilot）
- [ ] **同点をランダムに選ぶ実装へのアサーションが flaky になっていないか**。
      候補が単一になる盤面を選ぶか、`Math.random` を固定する

## ドキュメント・issue 運用

- [ ] **ファイルパスは実在するフルパスで書いたか**。`deploy.yml` ではなく
      `.github/workflows/deploy.yml`。書いたパス全件の実在を `ls` で確認する（#360 Copilot）
- [ ] **「〜のみ」「すべて」「完成」という断定に裏取りがあるか**。「CI は Node 22」と
      書く前に全ワークフローを grep する（e2e.yml だけ 20 だった実例）。
      「修理は PAT 更新のみ」には別エラーの調査が残っていた（#360 codex / Copilot）
- [ ] **issue 一覧は limit なしで全件取得したか**。`--limit 50` で #96 未満を見落とし、
      カバレッジ閾値 #35 と実装済み UX issue 群がガイドから漏れた（#360 codex）
- [ ] **「実装済み」と主張する前に issue の条件と実コードを突き合わせたか**。
      タイトルだけ見て閉じると誤る。本文が空の issue は判定基準を明記してから閉じる（#360 codex）

## レビュー対応の作法

- [ ] 指摘には**対応コミットのハッシュを明記して返信**する
- [ ] 対応済みスレッドは Resolved にする
- [ ] 指摘が正しくても、**自分の変更が原因かどうかは切り分けて明記**する
      （main 由来の問題なら別 issue に切り出す）
- [ ] **本ファイルに指摘を追記したか**（運用ルール 1）
