# プロンプティング技法リファレンス

> 参照元: https://github.com/shanraisshan/claude-code-best-practice
> Boris Cherny（Claude Code 開発者）および Claude Code チームの tips を元に構成

## 原則：マイクロマネジメントしない

**What（何を達成したいか）** と **制約（守るべき条件）** を渡せば十分。
How（どう実装するか）は Claude に委ねる。

```
# 良い例
「パスの判定ロジックにバグがある。
 症状: 両者がパスしてもゲームが終わらない。
 制約: 既存のテストを壊さないこと、shouldPass 関数を修正すること」

# 悪い例
「shouldPass.ts の12行目を変えて、次に game.ts の45行目を...」
```

## Challenge パターン（品質引き上げ）

実装完了後に品質をワンランク上げるためのプロンプト。

### コードレビュー Challenge

```
この変更について厳しく問い詰めて。
テストが全部通るまで「完了」と言わないで。
```

### リファクタ Challenge

```
今の知識を踏まえた上で一度リセットして、
最もシンプルで読みやすい実装を最初から作り直して。
```

最初の実装で問題点を学習した後に使うと最も効果的。

### 自己検証 Challenge

```
完了したら、別の視点から自分の実装をレビューして。
見落としや改善点があれば指摘して。
```

### 動作証明 Challenge

```
この変更が正しく動くことを証明して。
変更前後の動作を比較して見せて。
```

## シナリオ別プロンプト

### バグ修正

```
[エラーログ or スクリーンショットを貼る]

症状: <何が起きているか>
期待: <本来こうなるべき>
制約: <壊してはいけないもの>

fix
```

詳細な手順は不要。ログを渡して症状・期待値を書けば十分。

### 新機能実装

```
# Plan Mode で開始してからプランに合意する

[要件を書く]
まずこの要件を分析して、実装プランを提案して。
（プランに合意したら実装に移る）
```

### TDD との組み合わせ（このプロジェクト）

```
/tdd で以下の機能を実装して：
- [機能の説明]
- テストリストを出力してから始めて
- npm run test:unit でフィードバックを確認しながら進めて
```

### E2E 検証

```
Playwright で以下のシナリオを手動検証して：
1. [操作手順]
2. [確認すること]

npm run test:e2e でテストを実行して結果を報告して。
```

### コードリーディング

```
この処理フローを説明して。
できれば ASCII ダイアグラムで流れを示して。
```

## スペック記述のコツ

大きな機能を依頼するときは構造化して渡す：

```markdown
## 目的
何を達成したいか

## 背景
なぜこの変更が必要か

## 要件
- 具体的な振る舞い1
- 具体的な振る舞い2

## 制約
- 技術的制約（例: 既存のテストを壊さない）
- 設計制約（例: Pinia Store のパターンに合わせる）

## スコープ外
- やらないこと（明示することで誤解を防ぐ）
```

### スペックに書かないこと

- 実装の詳細手順（Claude が判断する）
- ファイル構成の指定（制約がない限り）
- 使うライブラリの指定（制約がない限り）

## 日常的な工夫

### 段階を分けて依頼する

大きなタスクは一度に投げない：

```
1. 「まず現状を調査して、課題を整理して」
2. （調査結果を確認）
3. 「では方針を提案して」
4. （方針に合意）
5. 「実装して」
```

### 音声入力の活用

タイピングより速く詳細なコンテキストを渡せる。
特にバグ報告や仕様説明など、文脈が複雑な場合に効果的。
