## 現時点の課題と解決順序

### ✅ Step 1 — リリースの詰まりを直す（#358・完了）

**課題だったこと**: release PR で必須 CI が起動せず auto-merge が BLOCKED のままになり、
毎リリース close → reopen の手動回避が必要だった（#342 で発生）。

**結果**: 解消済み。release PR は #375（1.14.2）→ #378（1.14.3）→ #381（1.15.0）と
**手動介入なしでマージできている**。

### 🔧 必須チェックが報告されない PR の扱い（#367・運用でカバー）

`ci.yml` の `paths` フィルタ対象外のファイル（`docs/**`、`.github/workflows/` の
一部、`eslint.config.mjs` など）だけを変更した PR は、必須チェック
（`lint-check` / `test-build`）が**一度も報告されず** `MERGEABLE / BLOCKED` のままになる。
CI をスキップする設定と、CI 合格を必須にする設定が噛み合っていないため。

**対処**: オーナーが内容を確認して管理者権限でマージする。

```bash
gh pr merge <N> --admin --merge --delete-branch
```

`paths` フィルタの撤廃（全 PR で CI を走らせる）も検討したが、オーナー 1 人の
リポジトリで詰まるのはアプリコードに影響しない変更が中心のため、設定を変えず
運用でカバーすることにした（#367）。

**留意点**: `--admin` は必須チェックを丸ごとバイパスする。**アプリコードを含む PR には
使わない**こと。複数人開発になったら `paths` 撤廃を再検討する。

### ✅ Step 3 — CPU の強さ改善（2026-07-27 完了・エピック #282 完走）

**課題だったこと**: 上級以上の CPU が弱すぎる（#357）。評価関数が石数差のみで、
探索も 2 手読み。中級（最大フリップ貪欲）と方向性が同じで差が出ていなかった。

**実施した順序と結果**:

| # | 内容 | 結果 |
|---|---|---|
| #357 | 評価関数を石数差 → 位置重み + mobility へ | 隅を取り、相手の選択肢を奪う挙動に |
| #372 | 終局はヒューリスティックでなく実際の石数勝敗で評価 | 読み切れる勝ちを捨てなくなった |
| #365 | ルートで alpha を伝播し αβ枝刈りを実際に発動させる | 評価ノード 107 → 33（-69%）・選ぶ手は不変 |
| #286 | 超上級（反復深化で最大 5 手読み） | UI に「超上級」を追加 |
| #379 | 思考時間をデッドラインで守る | 重い局面でも 1 秒で打ち切り |
| #287 | 達人 | **クローズ**（下記） |

**「達人」を作らなかった理由**: 当初は「超上級で αβ、達人で位置評価テーブル」と
段階を分ける計画だったが、#357 の解決策として**位置評価テーブルを上級の時点で導入**した。
結果、達人の構成要素はすべて超上級までに実装済みとなり、#287 は既存実装の焼き直しに
なるためクローズした。UI で選べるのは **初級・中級・上級・超上級の 4 段階**。

**この過程で得た設計上の教訓**（`/review-checklist` に反映済み）:

- **評価が先、探索が後**: 探索は評価関数の良し悪しを増幅するだけ。石数差評価のまま
  深く読むと「悪手を確信をもって選ぶ」CPU になる
- **深さは所要時間を保証しない**（#379）。「depth 5 なら 3 秒以内」は計測した局面が
  たまたま軽かっただけで、別環境では 6.7 秒かかった。**時間制約は時間で守る**
  （反復深化 + デッドライン）。ベンチは平均ではなく最悪ケースで判断する
- **勝率測定は開発時スクリプトで行い、CI に自己対戦テストは入れない**。
  重い・flaky・決定論スナップショットで価値が低いとして削除した経緯がある（#337）

**さらに強くする場合**: #96 MCTS / #97 完全読み / #98 評価関数チューニング /
#100 AI vs AI / #139 Web Worker で追跡する。

## 3原則（更新版）

1. **修理は機能より先** — リリースパイプラインの詰まり（#358）は全成果物に影響する。
   ダムの上流から直す
2. **台帳を正しくしてから選ぶ** — 実装済み issue（#284 等）を閉じないと、
   優先順位の判断が古い情報の上に積み上がる
3. **評価が先、探索が後（AI）／ 制約は同じ単位で守る** — 探索は評価関数を増幅するだけ。
   また「3 秒以内」のような時間制約を深さなどの固定パラメータで代用しない（#379）
